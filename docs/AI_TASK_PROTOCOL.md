# AI_TASK_PROTOCOL.md — Protocolo Obligatorio para Cada Cambio

> Este documento define **cómo** debe trabajar una IA en este repositorio.
> Es complementario a `AGENTS.md` (qué hacer y qué no) y `SPEC.md` (qué
> construir).

---

## Fases del Protocolo

Cada tarea pasa por **5 fases obligatorias**:

```
1. ENTENDER  →  2. PLANIFICAR  →  3. IMPLEMENTAR  →  4. VERIFICAR  →  5. REPORTAR
```

Saltarse una fase introduce bugs. Saltarse dos rompe el proyecto.

---

## Fase 1 — ENTENDER

### Preguntas obligatorias antes de tocar nada

1. **¿Qué pide el humano EXACTAMENTE?**
   - Si la petición es ambigua, pregunta. Una sola pregunta clarificadora
     vale más que 500 líneas de código mal dirigido.

2. **¿A qué sección de `SPEC.md` corresponde esta tarea?**
   - Usa `docs/FORMAT_SPEC_INDEX.md` o la tabla de §9 de `AGENTS.md` para
     localizarla.
   - Lee esa sección completa antes de avanzar. No "saltees al code".

3. **¿En qué fase del roadmap (`SPEC.md` §21) estamos?**
   - Si la tarea es de una fase futura, dilo al humano y confirma si
     se acepta adelantar.

4. **¿Esta tarea afecta el formato `.sdoc`?**
   - Si sí, `docs/FORMAT_SPEC_INDEX.md` es lectura adicional obligatoria.

5. **¿Hay riesgos?** (seguridad, breaking changes, perf, multi-servicio).
   - Si sí, pasa a Fase 2 con plan formal. Si no, plan implícito está OK
     para tareas triviales (1–2 archivos).

### Output de Fase 1

Un párrafo (4–6 líneas) al humano:

> *"Entiendo que necesitas X. Esto cae en `SPEC.md` §Y. Voy a tocar
> aproximadamente N archivos en las carpetas A, B. ¿Es correcto?"*

Si la tarea es trivial (cambiar un texto, fix de tipo), puedes saltarte
el "¿es correcto?" y pasar directo a Fase 3.

---

## Fase 2 — PLANIFICAR

Obligatorio cuando la tarea afecta **uno o más** de estos:

- Más de 5 archivos nuevos o 10 modificados.
- Seguridad (auth, cifrado, firmas, Vault, mTLS, OPA, Keycloak).
- Eventos Kafka (nuevo topic, cambio de schema, nuevo consumer/producer).
- Schemas de DB (Flyway migrations).
- El formato `.sdoc` (cualquier parte de `manifest`, `content`, `assets`,
  `revisions`, `sync`, `permissions`, `security`, `preview`).
- API pública (endpoints, contratos OpenAPI).
- Configuración del gateway o filtros globales.
- Nuevas dependencias.
- Renombrado de algo público.

### Estructura del plan

```
## Plan: <título corto>

### Contexto
- Sección de SPEC.md: §X
- Fase del roadmap: N
- Riesgos: [list]

### Archivos a tocar (rutas exactas)
- [CREATE] path/al/archivo.ts
- [MODIFY] otro/archivo.java
- [DELETE] viejo.yaml

### Pasos
1. ...
2. ...
3. ...

### Verificación
- Cómo probarlo (comando, URL, test).

### Qué NO voy a tocar (explicitamente)
- ...
```

**Envía el plan al humano. Espera aprobación antes de ejecutar.**

Si el humano dice "dale" / "ok" / "procede" → Fase 3.
Si el humano modifica el plan → re-emite plan corregido.
Si el humano dice "no" → para. No insistas.

## Fase 3 — IMPLEMENTAR

### Reglas absolutas

1. **Cambios mínimos suficientes.** Si la tarea es "fix bug X", arregla X.
   No refactorices nada más. No actualices imports "para limpieza". No
   reformatees archivos. No renombres variables al paso.

2. **Sigue convenciones del archivo que editas.**
   - Si el archivo usa 4 espacios, usa 4 espacios.
   - Si usa comillas dobles, usa dobles.
   - Si usa snake_case en variables, no metas camelCase.

3. **Patrones del proyecto se respetan.** Cada microservicio Java sigue
   la estructura `config/`, `controller/`, `service/`, `repository/`,
   `domain/`, `client/`, `kafka/`, `exception/`. **No inventes capas
   nuevas.**

4. **Sin "TODO" futuros.** Si no puedes terminar una tarea, **díselo al
   humano**. No dejes `// TODO: arreglar después`. No dejes funciones
   medio-implementadas.

5. **Sin atajos.** Si la spec exige Outbox Pattern para eventos, úsalo. No
   "por ahora hago `kafkaTemplate.send()` directo y después lo arreglamos".

6. **Cero secretos en el código.** Nunca `String API_KEY = "sk_live..."`.
   Siempre Vault o variables de entorno.

7. **Logging estructurado:** usa el patrón JSON Logback de
   `SPEC.md` §Componente I. Claves en inglés, mensajes en inglés.

### Antipatrones explícitamente prohibidos

| Antipatrón | Por qué |
|---|---|
| `// AI-generated` o `// Generated by Claude` | Prohibido (`AGENTS.md` §4) |
| `Co-Authored-By: Claude` en commits | Prohibido |
| `// FIXME later` o `// HACK` | Si está mal, arréglalo bien |
| `catch (Exception e) {}` (swallow silencioso) | Logueá y/o relanza |
| `if (env === 'demo') skipAllSecurity()` | Demo mode no es para saltar seguridad |
| Crear `release/`, `marketing/`, `notes/` en repo | Va fuera (`_personal/`) |
| `git push --force` sin permiso | Prohibido |
| `--no-verify` en commits | Prohibido |
| Usar `npm install <paquete>` sin permiso | Pregunta primero |

### Estilo de código

- **Java**: Spring Boot conventions, Lombok donde aplica, MapStruct para
  DTO mapping, Records para events/DTOs inmutables, Virtual Threads
  habilitados (Java 21).
- **Python**: type hints obligatorios, async/await en handlers FastAPI,
  Celery tasks con `bind=True` cuando necesitan auto-retry.
- **TypeScript**: strict mode, sin `any` (preferí `unknown` o tipos
  específicos), React 18 hooks, Zustand con **selectores granulares**
  (`useStore((s) => s.field)`, **no** `useStore()` desestructurando todo).
- **CSS**: CSS Modules en frontend (`Component.module.css`).
- **SQL**: migraciones Flyway versionadas (`V<n>__descripcion.sql`).

### Tests

- **Java**: JUnit 5 + AssertJ + Testcontainers (Postgres/Kafka/Redis).
- **Python**: pytest + pytest-asyncio + httpx para API tests.
- **TypeScript**: Vitest.

Si tocás `service/`, `domain/`, `kafka/` o `client/` en backend, escribí
al menos un test. Si tocás un hook complejo o un store en frontend, test
unitario.

## Fase 4 — VERIFICAR

**Antes de declarar la tarea completa**, ejecuta:

### Backend Java

```bash
./gradlew :services:<servicio>:build
./gradlew :services:<servicio>:test
```

Si tocaste algo que arranca el servicio, además:

```bash
./gradlew :services:<servicio>:bootRun
# y curl http://localhost:<puerto>/actuator/health → debe ser {"status":"UP"}
```

### Backend Python

```bash
cd services/render-service
pytest tests/ -v
# y arranca el servidor:
uvicorn app.main:app --reload --port 8086
# luego curl http://localhost:8086/health
```

### Frontend

```bash
cd apps/web
npm run typecheck     # tsc --noEmit
npm run build         # vite build
npm run dev           # luego abre http://localhost:3000
```

Mientras está abierto:
- Abre DevTools → Console. **No debe haber errores.**
- Recorre las rutas afectadas.
- Si tocaste UI, prueba responsive (375px, 768px, 1440px).
- Si tocaste algo de tema, prueba modo claro y oscuro.

### Cambios al formato `.sdoc`

Si tocaste algo del formato, además:
- Genera un `.sdoc` de ejemplo y vuélvelo a leer.
- Valida el resultado contra el JSON Schema.
- Si lo firmaste, verifica la firma.

### Infraestructura

Si tocaste docker-compose, helm, k8s:

```bash
docker compose -f infrastructure/docker/docker-compose.yml config
# valida sintaxis sin levantar
```

```bash
helm lint infrastructure/k8s/helm/sdoc/
```

### Si algo falla

**NO ocultes el error.** No marques la tarea como completa. Reporta al
humano:

> *"Implementé X. Sin embargo, [test/build/runtime] falla con [error
> exacto]. ¿Quieres que profundice en este error o prefieres revisar
> antes?"*

## Fase 5 — REPORTAR

### Formato del reporte de cierre

```
## Cambio: <título corto>

### Qué hice
- [bullet 1]
- [bullet 2]

### Archivos tocados
- path/exact/al/archivo.ext (CREATE | MODIFY | DELETE)
- ...

### Sección de SPEC.md aplicada
- §X

### Tests
- [pasaron | fallaron | no aplican]

### Verificación manual
- [qué probé y resultado]

### Pendientes / Riesgos
- Si hay algo abierto, dilo aquí.
- Si encontré algo raro en otra parte del repo (no relacionado a esta
  tarea), lo menciono y NO lo arreglo solo.

### Siguiente paso sugerido
- (opcional) Si veo el siguiente movimiento natural, lo propongo.
```

```bash
git push origin main                    # NUNCA --force sin permiso
```

## Plantilla de Commit Message

```
<tipo>(<scope>): <subject corto, imperativo, < 70 chars>

<body opcional: por qué del cambio, no qué — el qué se lee del diff>

<footer opcional: refs a issues, breaking changes>
```

**Tipos válidos:** `feat`, `fix`, `docs`, `style`, `refactor`, `perf`,
`test`, `chore`, `build`, `ci`.

**Scopes comunes:** `auth`, `document`, `sync`, `asset`, `version`,
`notification`, `render`, `gateway`, `web`, `format`, `infra`, `ci`,
`deps`.

**Prohibido:**
- Emojis en el subject.
- `Co-Authored-By: <cualquier IA>`.
- "Generated with", "AI-assisted", etc.

## Cuando Encuentres un Bug Mientras Hacías Otra Cosa

1. **NO lo arregles silenciosamente.**
2. Reporta al humano: "vi este bug, ¿lo arreglo en este PR o lo dejo para
   otro?"
3. Si el humano dice "arréglalo", arréglalo con commit separado y mensaje
   propio (`fix(scope): descripción`).
4. Si el humano dice "déjalo", crea un issue o anótalo en
   `docs/runbooks/known-issues.md`.

---

## Cuando Algo de `SPEC.md` te Parezca Contradictorio o Inviable

1. **NO lo cambies tú.**
2. Reporta al humano con cita exacta:

> *"§X dice [cita]. §Y dice [cita]. Veo conflicto en Z. ¿Cómo procedo?"*

3. Espera respuesta.
4. Si el humano decide cambiar la spec, **él edita `SPEC.md`**, no tú,
   salvo que te lo pida explícitamente.

---

## Resumen de un Vistazo

```
ANTES de cualquier acción:
  □ Leí AGENTS.md
  □ Leí la sección de SPEC.md que aplica
  □ Entendí qué pide el humano

DURANTE:
  □ Cambios mínimos suficientes
  □ Sin refactors no pedidos
  □ Sigo convenciones del archivo
  □ Sin secretos en código
  □ Sin TODOs futuros
  □ Sin atajos
  □ Sin menciones a IA

DESPUÉS:
  □ Compila / pasa tests
  □ Probado manualmente si aplica
  □ Reporte estructurado al humano
  □ Sin force push, sin destructivos
```
